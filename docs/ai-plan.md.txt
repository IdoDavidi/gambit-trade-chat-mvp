# AI Plan

## Overview

This plan implements the Human Plan using a React-based application centered around an LLM harness and a dedicated tool layer.

Eeact was selected because the assignment requires
a chat-first experience with a live state-driven GUI mirror.
React's component and state model naturally support this interaction pattern.

The implementation prioritizes:

- clear tool boundaries
- explainability
- traceability
- maintainable architecture

over broad feature coverage.

The goal is to demonstrate a chat-first trade-building experience rather than a complete NBA trade platform.

## Architecture

The system consists of five primary layers:

### User Interface

Responsible for:

- Chat interface
- Trade state visualization
- Verdict display

Files:

- ChatPanel
- TradeMirror
- VerdictPanel

---

### LLM Harness

Responsible for:

- system prompt
- conversation history
- available tools
- tool execution loop
- assistant responses

The harness acts as the single entry point for all model interactions.

Files:

- llmHarness.ts
- toolRegistry.ts

---

### Tool Layer

The model does not directly mutate state.

Instead it selects tools.

Initial tools:

- set_teams
- add_player
- remove_player
- clear_trade
- request_verdict

Each tool performs one deterministic action.

Example:

Tool:
add_player

Input:
playerId

Output:
Player added successfully
Current trade state updated

---

### Trade State

A single shared trade state object acts as the source of truth.

The following systems read from the same state:

- Chat
- Tool Layer
- Verdict Processing
- GUI Mirror

This prevents synchronization issues.

Trade state is owned by the application, not the model.
The model proposes actions through tools.
The tool layer is responsible for mutating state.

---

### Validation Layer

Validation responsibilities are isolated behind a service layer.

Possible implementations:

- Real bball-GM API
- Mock validation adapter

Validation implementation remains replaceable.

The remainder of the system should remain unchanged regardless of which implementation is used.

---

## Agentic Tool Loop

The application follows the required agentic workflow.

Example:

1. User submits message.
2. Harness sends message to model.
3. Model selects tool.
4. Tool executes.
5. Tool result returns to model.
6. Model decides whether another tool is required.
7. Process repeats until the turn is resolved.
8. Assistant produces final response.

---

## State Model

Trade state should contain:

### Teams

Current trade participants.

Example:

- Boston
- Miami

### Players

Players included in the trade.

### Verdict

Latest validation result.

### History

Record of trade modifications.

Used for:

- explainability
- traceability

---

## Explainability Strategy

Trade verdicts should be transformed into conversational responses.

The user should see:

- validity status
- summary explanation
- team salary information
- violations
- relevant rule references

The user should never be required to read raw JSON.

---

## Traceability Strategy

Each user action should be reconstructible.

Example:

User:

"Send Player A to Team B"

Result:

- Tool called: add_player
- Trade state updated
- GUI updated
- History entry recorded

This allows the user to understand how the system reached the current state.

## Risks

### API Availability

The validation service may not be publicly accessible.

Mitigation:

Maintain a validation abstraction supporting both real and mock implementations.

### Scope Expansion

Additional trade functionality may significantly increase implementation complexity.

Mitigation:

Maintain MVP boundaries defined in Human Plan.

### State Desynchronization

Chat and GUI could diverge.

Mitigation:

Use a shared trade state object as the single source of truth.

---

## Success Criteria

The implementation succeeds if:

- The user can describe a trade in natural language.
- The model uses tools to update trade state.
- The GUI mirrors the latest trade state.
- A verdict can be generated.
- The verdict appears in both chat and GUI.
- Users can understand why a trade is valid or invalid.
- Users can trace what changed after each interaction.
